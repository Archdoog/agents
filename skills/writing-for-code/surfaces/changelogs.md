# Changelogs and Release Notes

Use flavored mode. Follow the repository's categories, version format, and release process.
Describe observable behavior for users or integrators, not the sequence of file edits.
Keep internal refactors out unless they change a supported contract or matter to the intended reader.

Name affected features and the conditions under which behavior changes.
For breaking changes, give the migration action and relevant version boundary.
Separate released behavior from planned work. Do not infer a release date from a merged change.
Keep compatibility limits and known problems that affect adoption.

Avoid generic claims such as improved performance without evidence.
If measurements exist, keep their workload, environment, units, and qualifications.
Use links for supporting detail, not as a replacement for the behavior description.
