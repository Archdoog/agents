# Pull Requests

Use flavored mode. Read repository instructions, the PR template, and recent accepted PRs first.
Keep required fields. Do not force a new format where one already exists.

Explain the problem and why the chosen change solves it.
Describe effects, important constraints, and trade-offs rather than listing the diff again.
Link the issue and supporting decisions when useful.
Name compatibility effects, migration work, or rollout risks that reviewers need to assess.

Report actual verification with commands or steps and their observed results.
Separate automated checks, manual checks, untested behavior, and checks blocked by the environment.
Do not replace evidence with "fully tested" or adopt test counts from another branch.
State a concrete review question when a decision still needs input.

For bodies over about 150 words, request the fresh-eyes review in [PRUNE.md](../PRUNE.md).
Keep required disclosures and testing sections even when pruning repeated prose.
